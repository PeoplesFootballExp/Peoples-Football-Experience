
# Summary

In order to ensure the game is always free, open-source, and fun, we need to establish some core pillars for the game. There are two different sides of these pillars, the game pillars and the development pillars. The game pillars focus on how the game should feel and play, focused on actual features in the game and how the game is presented. The development pillars, are focused on how the game should continue to be developed, in order to ensure the game continues to be scalable, reliable, and performant. 


# Game Core Pillars

1. **100% Free and Fair Forever**: No Ads, no microtransactions, no annual re-buys. The game belongs to the people.
2. **Deep Tactics Meets Dynamic Action**: Manage like a Director of Football, then step on the pitch or watch match engines unfold in real time.
3. **Truly Global & Uncut**: Every country, dependency, and deep league pyramid represented, celebrating real local football culture (chants, dynamic flags, national pride).
4. **Total Freedom & Customization**: Edit anything in-game or load massive community database instantly via simple CSVs. 
5. **Play Anywhere (Optimized Performance)**: Ultra-fast simulation speed designed to run smoothly on low-end mobile devices, handhelds, and PCs alike.



## **1. Free to Play**

### Free to all players

This game will be free to all players. This was done to hopefully ensure that all players can access the game regardless of their financial standing. Free means that anyone in the world can download the game and play it.

# Development Core Pillars

1. **GPL v3.0 Open Source Integrity**: Code, art, music, and data are community-owned. No proprietary lock-in; the game lives forever.
2. **Single-Player and Local-First Priority**: Core Engine Loop, SQLite Database, and Rust logic must prioritize offline stability, local performance, and player privacy before any networked features
3. **Zero Monetization Standard**: Code contributions must never introduce ad frameworks, telemetry/trackers, paywalls, or artificial time-gated mechanics. 
4. **Data Neutrality and Hyper-Moddability**: Core engine must strictly separate game code from data structures, enabling complete overwrite capabilities via external files (CSVs/mods)
5. **Broad Device Scalability**: Every major backend system must be benchmarked for resource efficiency to maintain mobile and low-spec PC compatibility.

## Single Player Priority

### Multiplayer Priority Games

Many sport games, or game in general today, seem to focus on multiplayer more than the single player experience. There are a lot of reasons for companies to do this, which some listened below. 

1. Monetization
2. Infinitely Replayable
3. Social Pressure
4. Resistance to Piracy

While some of theses have their merits, it often times leads to single player experiences suffering as a result. After all, every company has limited time and resources to dedicate to games. Multiplayer, being a more profitable model, often brings in the most attention. 

### Why Single Player Focused

Being a single player focused game ensures that the multiplayer aspects of the game come second before single player experiences. There are two major reasons for doing this

1. Ownership
2. Offline Play

Ownerships means that once the game is installed, the game is yours forever. With multiplayer, there is often a reliance on the company to maintain central servers for the players to even have access to the game. This is great for game that live for a long time (e.g. Fortnite) but means you may lose access to your game if the company stops developing the game or retire the game. For example, the FIFA series (now known as EA Sports FC) relies on an annual release schedule, resulting in older titles losing their multiplayer servers entirely. There are even some games, such as The Crew, that are simply not playable anymore due to servers being shut down. 

Gamers have shown their widespread frustration with multiplayer games dying once servers are turned off. They can feel as if their money was effectively stolen if they paid for a games that years later the license is revoked or the servers shut down. This widespread frustration even lead to the "Stop Killing Games" movement, which aimed to legally require publishers to leave games in a reasonably playable state when official support dies. With a single player focus, this would not be a possibility since the game is designed to be owned by the player and they always have access to it.

Single Player focus also allows for more offline gaming. This is great for players who may not have the best internet connection or simply want to have access to their game no matter their connection availability. For example, offline play would allow for the game to be played in planes, trains, or even on top of a mountain. Online connection would only be required for the initial download and for future updates.

### Multiplayer as a Secondary Focus

While the single player experience is the priority, this does not mean multiplayer will not be available. This model simply flips the common philosophy of multiplayer on its head. Instead of multiplayer being only priority, multiplayer is an addition to an already good single player experience. One to one multiplayer would be the first addition, with more squad based multiplayer being the end goal eventually. In essence, the single player experience should be fun with multiplayer meaning you share this joy with friends or strangers.

## Data Neutrality and Hyper-Moddability

The core engine must remain a completely neutral execution framework. Game logic written in Rust must never hardcode team names, player attributes, league standings, or specific rules. Everything that defines the football world must live in external data files (CSVs, SQLite, TOML) that can be overridden at runtime or by the player. 

### The Game Architecture

To achieve blazingly fast stimulation speeds and total moddability, this project relies on **Data-Oriented Design (DOD)** powered by an **Entity Component System (ECS)** 

1. **Entities (The "IDs")**: A player, team, or match is just a lightweight integer ID. It holds no logic and no data on its own.
2. **Components (The "Data")**: Pure data structures containing raw values. They should contain zero functions of logic
3. **Systems (The "Logic")**: High performance Rust functions that run over entities that share specific components.

At first, this architectural decision may seem odd, given most games today rely on Object Oriented Programming (OOP). But, there are many benefits to this system outlined below

#### Pros
1. **Unmatched Cache Efficiency & Speed**: The way that DOD organizes memory, it leads to much more cache efficiency and allows us to stimulate thousands of changes across the game in milliseconds.
2. **Infinite Runtime Moddability**: Because systems process components data abstractly, changing how a team or player behaves requires zero recompiling. Swapping a CSV files or modifying an SQLite table changes game attributes dynamically. This allows players to change their game as much as they want and allows for more avenues of customization.
3. **Modular Composition over Rigid Inheritance**: With composition, adding new components/systems (or removing) becomes a much easier process. This allows for easier modding by the community and much more flexible programming experience. This makes future additions and maintainability much easier. This allows allows us to swap in and out new systems, without breaking the game instantly. 
4. **Seamless Parallel Processing**: Because systems operate on distinct, isolated arrays of components, Rust can safely run calculations in parallel across multiple CPU threads without lock contention or data races. This speeds up the game and allows for easier parallelism.

#### Cons
1. **Steeper Learning Curve**: Most developers are taught Object-Oriented Programming (OOP). Shifting to Data Oriented Design or Entity Component Systems requires thinking in a new way, which can feel counterintuitive at first.
2. **Abstract State Management**: Complex conditional relationships require careful system sequencing and event queues rather than simple if/else statements
3. **Strict Architectural Discipline**: Requires strict architectural discipline even with edges cases where OOP would be better. 
4. **Lose the Benefits of OOP**: OOP does have some benefits such as inheritance and hierarchal data representation which this new architecture would lose out on.

This means that any new code contributions should not plan to break this architectural decision. This decision was made to gain the benefits listed and ensure the longevity, moddability, and performance of the game.
